#### T3.1.1 `/api/data` 响应体膨胀检查（一期遗留的待决项）

`models` 子结构会随会话明细一并返回，而 `/api/data` 是**唯一返回会话明细**的端点（改造前约 209KB）。
其余端点不受影响（`/api/today`、`/api/all` 只返回汇总；同步导出走白名单会自动丢弃 `models`）。

- [ ] **先实测**：对比改造前后 `/api/data?agent=agy&mode=session` 的响应体大小
- [ ] **决策规则**：
  - 增幅 **≤ 30%** → 不处理（本地回环，影响可接受）
  - 增幅 **> 30%** → 实施剥离：在 `/api/data` 序列化前**构造新 dict** 并移除 `models`
- [ ] ⚠️ **若实施剥离，严禁用 `pop()` 原地修改条目** ——
      聚合结果的条目元素仍与适配器缓存共享，原地修改会造成**上游缓存污染**
      （这是此前修复过的严重缺陷类型）。必须构造新 dict：

```python
# 正确做法（新 dict，不动原对象）
def _strip_models(entry: dict) -> dict:
    e = dict(entry)
    e.pop("models", None)
    return e
```

### T3.5 多端同步决策 ⚠️（需要 WW 拍板）

当前 `sync._make_local_entry()` 是**字段白名单重建**，`models` 会被**自动丢弃** —— 即
**默认行为 = 模型维度仅本机可见，不会跨端同步**。

| 选项 | 说明 | 风险 | 建议 |
|---|---|---|---|
| **A. 保持丢弃**（默认） | 模型维度仅本机可见 | 零 | ✅ **推荐** |
| **B. 扩展白名单让 models 跨端同步** | 需改 schema、扩展合并逻辑、分片体积增大 | 中高 | 🟡 建议另立一期 |

**建议选 A 的理由**：
1. `models` 是明细数据，会让分片体积明显增大（每个会话条目都带一个子字典）；
2. 异机合并逻辑当前是**按 `sessionId` 去重**，支持多模型的话要扩展为按 `(sessionId, model)` —— 
   会改动刚修好的跨设备隔离机制，**风险不成比例**；
3. 属于「锦上添花」，不影响核心价值。

- [ ] 与 WW 确认选项
- [ ] 若选 A：**什么都不做**（但要在此确认，避免后面被当成遗漏）；在报告里明确记录该决策
- [ ] 若选 B：**必须**同步扩展 `_make_local_entry` 白名单与 `load_remote_devices_data` 的合并键，
      并重跑「跨设备重复 sessionId = 0」的隔离性验证（这是硬门槛）
