## 2. 共用模式说明

三个适配器都遵循**同一模式**（但实现差异较大，**不建议强行抽象成公共函数** —— 硬抽象会让三处都变得难读）：

```
① 在扫描/查询的循环外（或循环中）确定"该会话的模型名"
② 把该模型名赋给该会话产生的所有 records（第 8 位）
③ records 结构仍为第一期的 8 元组契约，不做任何变更
```

**关键前提**：由于 `records` 现在自带 model，而适配器已有「文件级缓存」机制
（`self._file_cache[fpath] = (mtime, size, records)`），
**模型名会自动进入缓存** → 额外的模型提取开销**只在冷扫时付一次**，热路径零影响。

## 3. 任务清单

### T2.1 `agy.py`：跨表取模型 + 会话级归属（本期核心）

#### 3.1.1 背景与已验证事实

| 事实 | 实测数据 |
|---|---|
| token 位置 | `steps.metadata`（`step_type=15`）的 protobuf **field 9** |
| 模型名位置 | `gen_metadata.data` / `executor_metadata.data`（protobuf blob） |
| **step 级能否关联** | ❌ **只有 47.4%**（`gen_metadata` 并非每个 step 都有对应 idx）→ **不要按 step 关联** |
| **会话（db）级归属** | ✅ **100%**（228/228 db 都能定出模型；13.9 亿 token 全部可归属） |
| 枚举占位符 | `MODEL_PLACEHOLDER_M319`(167 db) / `M299`(26) / `M318`(18) / `M36`(4) 等 |
| 真实名 | `gemini-3.8-flash`(182 db) / `gemini-3.8-flash-medium`(169) / `gemini-3.7-flash`(29) 等 |

#### 3.1.2 实现要点

- [ ] **在同一次 SQLite 连接内**额外查询模型 blob（避免二次开库）：

```python
# 在一次 conn 内完成
c.execute("SELECT metadata FROM steps WHERE step_type = 15 AND metadata IS NOT NULL")
steps_rows = c.fetchall()
# 新增：会话级模型来源
model_blob = b""
for tbl in ("gen_metadata", "executor_metadata"):
    try:
        c.execute(f"SELECT data FROM {tbl} WHERE data IS NOT NULL")
        model_blob += b"".join(r[0] for r in c.fetchall() if isinstance(r[0], bytes))
    except Exception:
        pass
db_model = extract_model_from_blob(model_blob)   # 见 3.1.3
```

- [ ] **在 records 循环外**确定 `db_model`，然后在 `records.append((..., db_model))` 时带上
- [ ] 模型名一律经 `normalize_model_name()`（第一期已在 `base.py` 提供）

#### 3.1.3 枚举映射方案（推荐「动态学习 + 持久化 + 原值兜底」三档）

实测已确认**同 db 内真实名与枚举共存**，且映射高度一致（M319→`gemini-3.8-flash` 81/108、M299→`gemini-3.7-flash` 16/17）。

**推荐方案**（自适应，不依赖硬编码表）：

```
优先级 1：blob 中直接出现真实模型名（正则 gemini-*/claude-*/gpt-* 等）→ 直接使用
优先级 2：查「学习到的映射表」把枚举翻译成真实名
          映射表的更新时机：每当某个 db 里「真实名」与「枚举」同时出现时，
          建立/投票更新 枚举→真实名 的映射（取多数票），并持久化
优先级 3：兜底 —— 未学习的枚举直接用其原值（如 model_placeholder_m26），
          保证「守恒」（token 不丢），只是显示名不够友好
```

- [ ] 实现 `extract_model_from_blob(blob) -> str`（正则 + 映射表查询 + 原值兜底）
- [ ] 实现映射表的**读取/合并/持久化**：
  - 路径：`~/.cache/myccusage/agy_model_enum_map.json`
  - 结构：`{"__schema__": 1, "map": {"MODEL_PLACEHOLDER_M319": {"gemini-3.8-flash": 81, ...}}, "updatedAt": "..."}`
  - 每次冷扫时按多数票合并；**写入要原子**（`os.replace`，与 `_save_persisted_file_cache` 同风格）
- [ ] 若实现映射表，**必须保证它的失败绝不影响主流程**（解析失败 → 退化为优先级 1/3）

> **不要**硬编码一张固定的枚举映射表 —— 它会随 Antigravity 版本变化而失效；动态学习 + 原值兜底才可持续。

#### 3.1.4 性能

| 项 | 实测 |
|---|---|
| 现状（仅 steps） | 124 ms（228 db 冷扫） |
| 加 gen_metadata 查询 | **181 ms（+45%）** |
| 热路径（有缓存） | **8~12 ms，无变化** |

- [ ] 性能目标：**冷扫增幅 ≤ 60%**、**热路径增幅 ≤ 5%**

### T2.3 `opencode.py`：`session.model` 解析 + 会话级归属

#### 3.3.1 已验证事实（含一个重要澄清）

| 事实 | 实测 |

> **重要**：**不要**用"28.6% 的会话覆盖率"来否定 opencode —— 它的 token 覆盖率是 **97.2%**。

#### 3.3.2 实现要点

- [ ] **主方案（推荐，简单）**：查询 `session` 表建立 `{sid: model}` 映射，在 `part` 循环里按 sid 取模型

```python
# 建映射（一次查询，会话级）
c.execute("SELECT id, model FROM session WHERE model IS NOT NULL AND TRIM(model) != ''")
sid_model = {}
for sid, raw in c.fetchall():
    try:
        mid = (json.loads(raw) or {}).get("id") or ""
    except Exception:
        mid = ""
    sid_model[sid] = normalize_model_name(mid)
# part 循环内
model = sid_model.get(sid, UNKNOWN_MODEL)
```

- [ ] **兜底来源也要带模型**：`session` 表兜底分支里，该会话本就有 model，直接使用
- [ ] `session.model` 为 `None` 的会话 → 记录为 `UNKNOWN_MODEL`（保持守恒，不丢 token）
- [ ] **备选增强（可选，若时间允许）**：改用 `message.data.model.modelID` 做**消息级**归属，
      可获得更高精度；但需先验证它与 `part` 的 step-finish 行能否按 message_id 对齐 ——
      **若无法可靠对齐，就用主方案，不要为此引入不确定性**
