# 按「模型维度」统计 Token / 调用次数 —— 可行性调研报告

> 调研日期：2026-09-24
> 调研方式：**全程只读**（未修改任何 Agent 数据、未改动项目代码；所有探测脚本均临时执行，工作区保持干净）
> 调研目标：判断能否以**高性能、简洁**的方式，按**实际使用的模型**维度拆分 token 量与调用次数

---

## 一、结论摘要（TL;DR）

**结论：完全具备实现条件，且比预期更简单 —— 8 个 Agent 全部拿得到模型信息。**

| 判断项 | 结论 |
|---|---|
| 数据是否可得 | ✅ **8/8 Agent 都能拿到模型名**（含此前完全没暴露的 grok） |
| 覆盖率 | ✅ 5 个可达**接近 100%**；其余为 95%+（残差是应过滤的合成消息） |
| 「按模型拆 token」口径 | ✅ 全部支持 |
| 「按模型计调用次数」口径 | ✅ **7/8 是原生字段或直接可数**，1 个需改用消息级计数 |
| 性能代价 | ✅ 5 个 Agent **零额外 I/O**（模型字段与 token 同行/同表）；仅 agy 需多一次表查询（+45% 冷扫，但走缓存后无影响） |
| 工程改造成本 | 🟡 **中等且是结构性的** —— 需要扩展数据契约（当前 7 元组 → 需加 model 维度）与缓存结构，不是加个字段那么简单 |

**一句话**：数据条件**完全具备**；真正的工作量在「数据契约与缓存结构的升级」，而不在「数据能不能读到」。

**一个额外的重要发现**：`hermes` 的 `state.db` 里有一张**专门的 `session_model_usage` 表**，原生带 `model` + `api_call_count` + 四类 token + 真实成本列 —— **这正是本需求想要的数据结构，但当前适配器完全没用它**（代码注释声称「读取 sessions 与 session_model_usage 表」，实际只读了 `sessions`）。

---

## 二、调研方法

1. **只读扫描**每个 Agent 的真实数据源（SQLite 以 `file:...?mode=ro` 打开，JSONL 只读遍历）；
2. 对**每一处**出现模型名的地方，确认它与 **token 字段是否同源**（同一行 / 同一表 / 需关联）；
3. 统计**覆盖率**：含 token 的记录中，有多少能定出模型；
4. 用**已有数据交叉验证**（如 claude 的 `assistant.usage` 与 `cost-state.modelUsage` 两个独立来源对比）；
5. 实测**性能增量**。

## 四、模型信息来源与实测覆盖率（核心）

按「数据来源的获取方式」分三类，**这决定了改造成本**：

### 第 1 类：SQLite 原生列 —— 最理想（加个 `GROUP BY` 就能出结果）

| Agent | 模型字段 | 实测 |
|---|---|---|
| **hermes** | `session_model_usage.model`（**专门表**，100 行） | ✅ **100%**。该表同时含 `api_call_count`（调用次数！）、`input_tokens`/`output_tokens`/`cache_read_tokens`/`cache_write_tokens`/`reasoning_tokens`、`estimated_cost_usd`、`actual_cost_usd` |
| **opencode** | `session.model` | ✅ 会话级原生。值为 JSON 串：`{"id":"gemini-3.8-flash-medium","providerID":"...","variant":"default"}`，需 `json` 解一次 |
| **workbuddy(db)** | `sessions.model` | ✅ 原生列 |

**hermes 实测按模型聚合（直接 SQL 即得，无需任何解析）：**

| 模型 | 调用次数 | Token |
|---|---:|---:|
| mimo-v2.5-pro | 16 | 83,858,084 |
| glm-5.2 | 18 | 47,997,643 |
| grok-4.6 | 4 | 19,005,018 |
| grok-4.3 | 5 | 17,658,979 |
| grok-4.5 | 12 | 10,609,839 |
| gemini-3.8-flash-medium | 17 | 6,436,338 |

> 这就是本需求最终想要的数据形态 —— **hermes 已经有了现成的**。

### 第 2 类：JSONL 同行字段 —— 改动极小（同一次解析顺手多读一个 key）

| Agent | 模型字段 | 与 token 是否同源 | 实测覆盖率 |
|---|---|---|---|
| **claude** | `message.model` | ✅ **同一个 `message` 对象内**（token 在 `message.usage`） | ✅ **95.3%**（510/535；残差 25 条是 `<synthetic>` 合成消息，**本就该过滤**） |
| **workbuddy** | `providerData.requestModelName` / `requestModelId` / `model` | ✅ 同一行 | ✅ 高（5328/6001 行含 `providerData.model`） |
| **codex** | `payload.model` | ✅ 同一行（payload 内） | 采样 235/6039 行含 model（与含 token 的行数量级一致，相对覆盖高） |
| **pi** | `message.model` / `modelId` | ✅ 同一行 | 采样 207 + 15 次命中 |

**claude 实测双源交叉验证**（这是最有力的数据可靠性证据）：

| 模型 | 源1 `assistant.usage` 逐次累加 | 源2 `cost-state.modelUsage` | 调用次数 |
|---|---:|---:|---:|
| mimo-v2.5-pro | 5,621,275 | 0 | 127 |
| gemini-3.8-flash | 1,481,149 | 0 | 155 |
| deepseek-v4-pro-0813 | 1,148,351 | 494,050 | 159 |
| glm-5.2 | 408,947 | 204,758 | 68 |
| grok-4.5 | 22,620 | 0 | 1 |
| gemini-3.8-flash-medium | 0 | 1,273,422 | 0 |

**关键判断**：
- **源1（`assistant.message.usage`）应作为主口径** —— 逐次精确、覆盖 510 次调用、且天然带调用次数；源2 只覆盖 19 个会话（`cost-state` 记录仅 33 条），是**不完整的汇总快照**。
- `cost-state.modelUsage` 的独特价值：**自带 `costUSD` 真实成本**，可作费用校准。
- ⚠️ **`cost-state` 是「同一数值重复写入」的快照**（实测：同一会话多条记录数值完全相同，如 `218822, 218822`），**绝对不能直接求和**，否则重复计数。正确做法是**每会话取最后一条**。

### 第 3 类：需要关联 / 归属 —— 需要额外逻辑，但成本可控

| Agent | 情况 | 实测方案与覆盖率 |
|---|---|---|
| **agy** | token 在 `steps.metadata`（protobuf field 9），模型名**不在**同一条消息里（实测 0% 重叠） | ⚠️ **step 级关联只有 47.4%**（`gen_metadata` 并非每个 step 都有对应条目）；<br>✅ **改用会话（db）级归属 → 100%** |
| **grok** | 模型在 `params.update._meta.modelId`，token 在 `params.update.usage` —— **同一对象的两处，但实测 0% 同行重叠**（有 usage 的 91 行都不含 modelId） | ✅ **会话级归属 = 100%**（28/28 会话都能定出模型，且 modelId 行数 ≈ usage 行数，说明只是记录分离而非缺失） |

**agy 会话级归属实测结果（推荐方案）：**

```

token 总量: 1,392,418,281 | 可归属到模型的 token: 1,392,418,281 (100.0%)
```

## 六、性能实测

| 场景 | 实测 |
|---|---|
| agy 现有全量扫描（有文件级缓存） | **8 ~ 12 ms** |
| agy 增加 `gen_metadata` 查询（228 db 冷扫） | 124 ms → **181 ms**（+45%） |
| claude / grok / codex / pi / workbuddy / hermes / opencode | **零额外 I/O** —— 模型字段与 token 同源（同行或同表），只是在既有解析路径上多读一个 key |

**结论**：
- **7/8 个 Agent 的性能影响是「零」**：不新增任何文件读取，只是解析时多取一个字段。
- agy 是唯一有增量的：需在同一 SQLite 连接内多发一条 `SELECT data FROM gen_metadata`（每库通常 1~2 行）。**实测 +57ms 只发生在全量冷扫的首次**；由于 agy 已有「文件级 mtime 缓存 + 进程内 `_full_cache`」，**热路径仍是 8~12ms，用户无感**。若把 model 一起写进文件级缓存，则该成本只在数据变更时付出一次。

## 七、工程改造成本评估

按工作量分级（**这是决策的关键，不是数据可得性**）：

| 层级 | 内容 | 涉及 Agent | 说明 |
|---|---|---|---|
| **L1 数据契约** | `_accumulate_records()` 当前接收 **7 元组**（sid, date, iso, inp, cr, out, tot），需扩展为携带 model 的维度 | **全部 8 个** | 建议改为 8 元组或 dict。这是**所有改动的公共前提**，`base.py` 一处改、8 处受益（正好复用已上提的 `_accumulate_records`） |
| **L2 缓存结构** | `_file_cache` / `_full_cache` 中存的 records 结构随之变化 → **旧缓存需失效一次**（可接受，一次性） | 全部 | 需注意 `~/.cache/myccusage/*_file_cache.json` 的兼容处理 |
| **L3 聚合层** | `daily_map` / `session_list` 的条目需带 model 维度，并新增「按模型汇总」的聚合出口 | `core.py` | 建议**新增**独立的 `get_model_breakdown()`，而不是改动既有 `get_daily_data` 的返回结构（**零回归风险**） |
| **L4 各适配器取 model** | 见下方分级 | — | — |
| **L5 展示层** | Web / Dock / CLI 新增「按模型」视图 | `web/`, `macos/` | 可选，可后置 |

**L4 各适配器取 model 的难度分级：**

| 难度 | Agent | 具体改动 |
|---|---|---|
| 🟢 极简 | **hermes** | 直接用现存的 `session_model_usage` 表（`SELECT model, SUM(...), SUM(api_call_count) GROUP BY model`），**连 token 提取逻辑都不用改** |
| 🟢 极简 | claude / codex / pi / workbuddy | 既有解析循环里多读一个 key（如 `msg.get("model")`），**约 1~3 行/适配器** |
| 🟡 简单 | grok / opencode | 会话级归属（从 session 上下文取模型名后下传给该会话的所有记录）；opencode 需 `json.loads(session.model)` |
| 🟠 中等 | **agy** | ① 多查一次 `gen_metadata`；② 建立 `MODEL_PLACEHOLDER_*` → 真实名映射；③ 采用**会话级归属**（实测 100%）而非 step 级（仅 47.4%） |

## 八、风险与注意事项

1. **模型名归一化是必须的**（否则同一模型会被拆成多行）：
   - 实测 workbuddy 同时存在 `Deepseek-V4.1-Flash`（5129 次）与 `deepseek-v4.1-flash`（72 次）—— **大小写不一致**；
   - 需统一 `lower()` + 别名归并（如 `gemini-3.8-flash-medium` 与 `gemini-3.8-flash` 是否合并要产品决策）。
2. **必须过滤的伪模型名**：claude 的 `<synthetic>`（25 条，零 token 的合成消息）、agy 的 `cli`/`auto` 之类非模型值。
3. **`cost-state` 的重复快照**：claude 若误用源2 求和会**重复计数**（实测同一会话 2~4 条数值完全相同），必须「每会话取最后一条」。
4. **agy 的 step 级关联只有 47.4%** —— **不要**按 step 关联，要按会话归属。
5. **跨 Agent 口径不一**：「调用次数」定义存在差异（见第五节），若用于横向对比需统一或标注。
6. **多端同步的影响**：若按模型维度进入同步分片，`export_local_snapshot()` 的**8 字段白名单**需一并扩展，且保持此前修复的「来源闸门」不变（否则会破坏刚修好的跨设备隔离）。

## 九、建议

**建议：值得做，且建议分期做。**

- **第 1 期（高性价比，建议先做）**：先做 **hermes + claude + workbuddy** 三个（都是 L4 极简档，其中 hermes 是现成表），配合 L1~L3 的公共改造，验证「数据契约扩展」这条主线的正确性。这三个已能覆盖你日常最大量的模型使用（workbuddy 的 5368 次调用 + hermes 的多模型分布）。
- **第 2 期**：补齐 grok / codex / pi / opencode（会话级归属模式，可复用同一套代码）。
- **第 3 期**：agy（需处理跨表查询 + 枚举映射，是唯一有性能增量的，但它是你用量最大的 Agent，值这个工作量）。
- **展示层**放在最后，且建议**新增独立视图**而非改动既有页面。

**架构上的关键建议**：
> 由于 `base.py` 已把 8 个适配器的累加逻辑上提为 `_accumulate_records()`，**L1 改一处即可覆盖全部 Agent** —— 这是此前那次重构带来的直接红利。建议在 `_accumulate_records()` 中把 model 作为**可选维度**（默认 `None`），这样：不关心模型的调用路径（如今日速报）**完全不受影响**，需要时再聚合 —— 既保证兼容，也不给热路径增加开销。
