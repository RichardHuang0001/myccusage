# 豆包工作（Doubao Work）统计适配 —— 技术架构与施工计划

> 状态：设计稿（待审批，未动代码）
> 日期：2026-11-24
> 前置结论：本地数据嗅探 + 开源社区调研 + 本机微基准实测（见 §6）

---

## 1. 目标与硬承诺

为 myccusage 新增第 10 个 Agent「豆包工作」，采用**定期增量抓取 + 丢失前固化**路线：
在豆包 LevelDB 把逐轮用量快照 compaction 丢弃之前，把数据安全固化到我们自己的账本里。

四条硬承诺（与项目现有承诺对齐）：

1. **零新增常驻进程**：采集完全嵌入既有常驻 daemon 的请求路径（程序坞 60s 轮询 / Web 心跳），不另起服务、不新增线程池、不改 Swift。
2. **开关关闭 = 零额外开销**：关闭时热路径只多一次内存布尔判断（~0µs），不做任何 stat / 文件读取，性能完全退化回当前基线。
3. **零第三方依赖**：Snappy / WAL / SSTable 解码全部纯 Python 自研（对标 `zstdcodec.py` 的地位），不移植开源整套读取器。
4. **不虚构口径**：本地拿不到的（计费 output / cache / 模型名映射）一律进 `gaps` 诚实上报，不用 0 或估值冒充真实口径。

## 2. 数据源与口径（诚实边界）

### 2.1 能拿到什么

| 数据 | 来源 | 留存特性 |
|---|---|---|
| 逐轮上下文用量 `context_window_usage`（system_prompt / messages / skills / tools / total_window_size） | 聊天 IndexedDB（LevelDB）消息元数据 | **易失**：挂在可变任务状态键上每轮覆盖，compaction 后旧版本丢失 → 必须定期固化 |
| 轮次身份与时间（conversation_id、task/section id、create_time_ms） | 同上 | 同上 |
| 会话清单（id / name / create_time / update_time） | `conversation-list-data-*` 键 | 较稳定，但同样会被覆盖更新 |
| 会话标题 / 创建时间 / 每轮需求 | 工作区 `.sessions/<sid>/assignment.md`、`board.md` | 持久，不丢 |
| 完整消息流水（无时间戳/无 Token） | 工作区 `trajectory.jsonl` | 持久，仅用作标题与活跃度兜底 |

### 2.2 拿不到什么（进 gaps，任何本地方案都补不齐）

- 计费口径的 `prompt_tokens` / `completion_tokens` / `cache_read_tokens`（全库结构化扫描证实本地不存在，社区最成熟解析器同样不提取）。
- 模型名称：本地只有数字 `model_id`（如 38），无名称映射表 → 统一 `UNKNOWN_MODEL`，原始 id 保留在 insights 里供未来对照。
- **覆盖窗口**：只有采集器运行期间产生的轮次能被固化；开关关闭或程序坞/网页都没开的时段，数据永久丢失。这是本路线的固有边界，UI 必须明示。

### 2.3 八元组口径映射（⚠️ 需拍板）

```
sid   = conversation_id
date  = 轮次 create_time_ms 归入自然日
iso   = 同上
inp   = system_prompt + messages + skills + tools   ← 上下文窗口占用（输入侧参考量）
cr    = 0（gaps 声明：缓存命中不可得）
out   = 0（gaps 声明：输出 Token 不可得）
tot   = inp
model = UNKNOWN_MODEL
```

**口径定性**：`inp` 是"该轮上下文窗口占用快照"，是真实测量值，但**不是计费 prompt_tokens**（不含逐轮累计、含系统提示/技能/工具占用）。
前端在豆包 Agent 视图顶部常驻一条口径说明横幅，insights 的 `gaps` 完整列出上述缺口。
费用折算沿用全站等效计价，但横幅注明"按上下文占用等效折算，非真实账单"。

> 备选口径（若审批认为上述映射有误导风险）：账本只记会话数/轮次数/活跃时长，Token 列全部留空进 gaps，用量细节只放 insights 专属 tab。代价是豆包无法参与全景 Token 对比。**默认推荐主方案**，与 dsh 的 gaps 范式一致。

## 3. 总体架构

```
┌─ macOS 程序坞 (Swift, 零改动) ─────────────────────────────┐
│  Timer 60s ──► GET /api/today ─┐                          │
└────────────────────────────────┼──────────────────────────┘
┌─ Web 看板 (页面打开时) ─────────┼──────────────────────────┐
│  sendPing 2.5s ─► GET /api/ping┤                          │
└────────────────────────────────┼──────────────────────────┘
                                 ▼
┌─ 既有常驻 Python daemon (8488, 零新增进程) ────────────────────────────┐
│                                                                      │
│  /api/today、/api/ping 处理器入口                                     │
│      └─► doubao_capture.tick()          ← 唯一嵌入点，两行调用         │
│            ① 开关布尔判断（关→立即返回，~0µs）                         │
│            ② 节流：距上次 tick < 30s → 返回                            │
│            ③ 非阻塞锁：已有 tick 在跑 → 返回                           │
│            ④ LevelDB 目录指纹（stat×N，~15µs；无变化→返回）            │
│            ⑤ WAL 增量尾读（offset 追踪 + 4KB 重叠窗）                  │
│               └─ 结构化定向提取 usage/轮次身份/会话清单（0.6ms/MB）     │
│            ⑥ 文件轮换/新 .ldb → Snappy+SSTable 追平（偶发冷路径）       │
│            ⑦ 按轮次去重（取最长快照）→ 追加固化账本                     │
│                                                                      │
│  ~/.cache/myccusage/doubao_journal.jsonl   ← 固化账本（append-only）   │
│  ~/.cache/myccusage/doubao_state.json      ← offset/指纹/去重索引      │
│  ~/.config/myccusage/doubao_config.json    ← 开关（默认 false）        │
│                                                                      │
│  adapters/doubao.py（常规适配器，按需读取，不参与 tick）                │
│      └─ 读 journal + 工作区元数据 → 8 元组 → 既有缓存/聚合/图表管线     │
│      └─ get_insights()：上下文构成、轮次结构、model_id、gaps            │
└──────────────────────────────────────────────────────────────────────┘
```

要点：

- **采集与展示彻底解耦**。tick 只负责"抢救数据进账本"，开销与用户看不看豆包视图无关；适配器只读我们自己的账本，开销与其他 Agent 的 JSONL 适配器同范式。
- **双驱动源**：程序坞 60s 轮询是主宿主；Web 心跳（节流到 ≥30s 一次）覆盖只开网页的时段。两者都没开 → 不采集（诚实边界，UI 明示）。
- **开关默认关闭**。用户在 Web 设置里打开后才开始积累数据；打开那一刻起的历史无法追回。

## 4. 模块设计

### 4.1 `myccusage_lib/idbcodec.py`（新增，解码内核，~300–400 行）

对标 `zstdcodec.py` 的零依赖内核地位。**只做定向提取，不做完整 V8 反序列化**——这是性能关键：

| 组件 | 用途 | 路径 |
|---|---|---|
| `extract_records(raw: bytes)` | 结构化模式提取：`context_window_usage` + 数值五元组、轮次身份、conversation-list 元数据。字节级定位，成本随扫描字节数线性（实测 0.6ms/MB），与快照结构深度无关 | 热路径 |
| WAL 尾读辅助 | 32KB 块边界处理 + 4KB 重叠窗，容忍半条记录；可选 CRC32C 校验防撕裂写 | 热路径 |
| `snappy_decompress(raw)` | Snappy raw block 纯 Python 解码（~60 行，varint + literal/copy） | 冷路径 |
| SSTable 读取 | footer → index block → data block（前缀压缩还原），仅用于新 .ldb 追平 | 冷路径 |

**自指污染防护（硬约束）**：豆包存储会实时记录"当前这段对话"，裸关键词扫描会命中我们自己的扫描命令回声。提取器只认"字段名 + 限定字节距离内的数值"结构化模式，且要求轮次身份字段共现；绝不按裸关键词计数。

### 4.2 `myccusage_lib/adapters/doubao_capture.py`（新增，采集引擎）

模块级单例状态 + `tick()` 入口，无类实例注册（它不是适配器，不进 ADAPTERS）：

- `tick()`：§3 流程。全程 try/except 收敛，任何异常只记日志、绝不影响 /api/today 主响应。
- **offset 追踪**：`state.files = {文件名: {size, mtime_ns, offset}}`。WAL 只读追加尾部；文件号前进（轮换）→ 旧文件若已被压缩则走 .ldb 追平，新文件从 0 读。
- **去重索引**：内存 dict `round_id → (total, ts)`，启动时从 journal 重建（journal 每轮 ~150B，万轮也才 1.5MB，重建 <50ms 一次性）。同一轮取 total 最大的快照（生成结束时的最终态）。
- **固化账本** `doubao_journal.jsonl`：append-only，每行 `{conv_id, round_id, ts_ms, usage:{...}, model_id, agent_name, conv_name?}`。同轮更新版本追加新行，读取侧取最大，写入侧永不改写历史 → 崩溃安全。
- **账本压实**：超过 5000 行或 2MB 时，一次性重写为"每轮最新态"（临时文件 + rename 原子替换），挂在 tick 尾部低频执行。
- **多 Profile**：枚举 `Profile */IndexedDB/chrome_doubao-chat_0.indexeddb.leveldb`，当前仅 Profile 1 活跃，其余目录不存在时零成本跳过。
- **配置**：`~/.config/myccusage/doubao_config.json`（照抄 sync_config.json 范式）：`{"enabled": false}`。daemon 启动加载进内存；`POST /api/doubao/config` 写文件 + 改内存布尔。**tick 热路径不读配置文件**。

### 4.3 `myccusage_lib/adapters/doubao.py`（新增，常规适配器）

继承 `BaseAgentAdapter`，完全走既有管线（指纹缓存 / today_only / `_accumulate_records` / 磁盘切片缓存）：

- `is_available()`：豆包数据根目录存在。
- `get_source_fingerprint()`：journal + state + 工作区 assignment/board 的 mtime 指纹（微秒级）。
- `fetch_data()`：读 journal（每轮取最大快照）→ §2.3 八元组；`get_titles_and_times()` 用 journal 内会话名 + 工作区 assignment.md 兜底。
- `get_insights()`：上下文构成四段占比、逐日/逐会话轮次结构、原始 model_id 分布、采集覆盖窗口（首条/末条固化时间）、完整 `gaps`。数据全部来自 fetch_data 已解析内容，**不新增文件扫描**（契约 3.1.1）。
- 注册四件套：`ADAPTERS` / `SUPPORTED_AGENTS["doubao"]={"name":"豆包工作"}` / cli `--doubao` / index.html agentSelector 按钮。

### 4.4 API 与前端

- `GET /api/doubao/status`：`{enabled, lastTickTime, capturedRounds, journalBytes, coverageSince, gaps摘要}` —— 供开关旁状态展示。
- `POST /api/doubao/config`：`{enabled}`，照抄 `/api/sync/config` 范式（写配置 → 内存生效 → 无需重启）。
- 前端：在既有设置模态框（syncModal 同区）加一行开关「豆包工作持续统计」+ 状态小字（已固化 N 轮 / 最近采集时间）+ 一句覆盖窗口说明。开关切换纯走 API，不触发全站重算。
- 豆包 Agent 视图：口径横幅（§2.3）+ insights tab 由既有能力探测自动出现，gaps 由既有渲染器原样展示。**全景对比 / 趋势图 / 模型视图零改动**（新 Agent 自动流入既有聚合）。

## 5. 关键机制与风险对策

| 风险 | 对策 |
|---|---|
| compaction 丢版本 | 60s 轮询远快于 WAL→L0→L1 合并窗口（分钟~小时级）；文件轮换检测 + .ldb 追平兜底 |
| 撕裂写 / 半条记录 | 4KB 重叠窗 + 结构化模式完整匹配才入账；可选 CRC 校验 |
| 自指污染 | 结构化数值模式 + 轮次身份共现要求（§4.1） |
| 豆包版本升级改存储格式 | 提取器模式失配时"静默零命中 + status 暴露 lastHit 时间"，不崩溃不虚构；版本跟进只需改模式常量 |
| 并发 tick（Dock 与 Web 同时驱动） | 非阻塞锁 + 30s 节流，天然幂等 |
| daemon 被 kill / 崩溃 | journal append-only + state 原子写；重启后从 offset 续读，最坏丢一个节流窗口内的增量（可被 .ldb 追平找回） |
| 开关关闭期间数据丢失 | 固有边界，UI 明示"关闭期间不采集且不可追回"；关闭即零开销是用户明确要求的取舍 |
| 账本无限增长 | 每轮 ~150B + 低频压实，重度使用一年约几 MB 量级 |

## 6. 性能预算与验收指标

本机实测基线（2026-11-24，真实豆包库）：指纹 14µs / WAL 定向提取 0.5–0.6ms/MB / 256KB 增量尾读 0.18ms。

**P1 解码内核实测校准（2026-11-24，idbcodec.py 落地后）**：
- Snappy 纯 Python 解压吞吐 **35MB/s**（仅压缩块）；因多数块为 raw 未压缩，冷路径整体有效吞吐 ~55MB/s。
- 当前库全文件冷解码 + 提取 **145ms**（约 8MB 解压量），落在 ≤300ms 预算内。
- 热路径 WAL 提取 **0.5ms/MB** 复测确认。
- 活体提取验证：usage 轮次身份齐全（message_id UUID / conversation_id / model_id / create_time_ms / section_tag），自指回声零混入；会话元数据 22 条、中文会话名（V8 双字节串）正常。
- **数据流失现场实证**：P1 施工期间库再次 compaction，数分钟前提取到的 2 个 usage 轮次已被丢弃归零——印证"定期固化、越早越好"的路线前提。

| 工况 | 预算 | 验收方法 |
|---|---|---|
| **开关关闭** | 热路径 +≤0.05ms（一次布尔判断） | /api/today 压测对比开关前后 p50/p99，差值在噪声内 |
| 开启 + 豆包空闲 | +≤0.1ms / tick（纯指纹） | 同上，空闲态采样 |
| 开启 + 豆包活跃 | +≤5ms / tick（2MB 尾读上限） | 真实生成期间采样 tick 耗时日志 |
| compaction 追平 | 单次 ≤300ms 尖峰，摊薄 CPU <0.5% | **P1 已实测：全量冷解码 145ms，达标** |
| 内存 | 稳态去重索引 KB~MB 级，无增长泄漏 | 24h soak 前后 RSS 对比 |
| 磁盘 | 每轮 ~150B 追加 + 低频压实 | journal 体量审计 |

对照现状：全 Agent 60s 刷新约 5ms、CPU 趋近 0%。**开启后空闲态总刷新仍 <5.1ms，"趋近 0%"承诺不变。**

## 7. 施工计划（4 阶段）

> 每阶段独立 git commit；涉及 daemon 行为的阶段结束时平滑替换本地进程（kill 旧 pid → 相同 PYTHONPATH 拉起 → /api/ping 验证，Dock App 不动）。
> **P2 结束即开始真实积累数据**——数据随时间永久流失，采集上线越早越好，展示可以后补。

### P1 · 解码内核 + 离线验证（不改任何主链路）

- 新增 `idbcodec.py`：结构化提取器、WAL 尾读、Snappy raw block、SSTable 追平读取。
- 临时原型脚本对活体豆包库做只读全量提取，与人工嗅探结果逐条对照；Snappy 用已知向量验证正确性。
- 实测 Snappy 纯 Python 吞吐，校准 §6 冷路径预算。
- 单元测试进 `tests/`（合成 fixture，不依赖活体库）。
- **验收**：活体库全部 usage 轮次提取无遗漏无回声污染；基准数字回填本文档。
- 产出：`idbcodec.py` + tests + commit。无进程操作。

### P2 · 采集引擎 + 开关 + 常驻嵌入（开始固化数据）

- 新增 `doubao_capture.py`（tick / offset / 去重 / journal / 压实 / state）。
- 配置 + API（status / config）+ 前端开关行。
- 嵌入 `/api/today` 与 `/api/ping` 入口（各两行调用，节流 30s）。
- CLI 调试入口 `--doubao-capture-once`（手动单步，便于排查）。
- **验收**：关闭态零开销回归达标；开启后真实使用豆包期间 journal 正确增长；kill -9 重启续读不丢不重。
- 产出：commit + **平滑替换 daemon**（从此开始积累）。

**P2 已完成（2026-11-24）**：关闭态 tick 实测中位 0.125µs / p99 0.25µs（零开销达标）；
`/api/ping` 活体驱动 tick 成功（lastTickTime 更新）；开关 API 双向热切换 + 配置持久化正常；
CLI 单步固化 55 条会话元数据；31 项测试全过（含相邻轮次身份去重回归）；
daemon 平滑替换（旧 36965 → 新 75087，Dock 3548 不动）；前端📡模态框 DOM 验证通过。
施工中修复 `_find_near` 取窗口首个匹配导致相邻轮次身份误配的缺陷（改为取最近匹配）。

### P3 · 适配器 + 看板展示

- 新增 `adapters/doubao.py` + 注册四件套 + 口径横幅 + insights（gaps 完整）。
- **验收**：daily / session / models / 全景对比四视图口径一致；`byDate` 求和恒等于 `models` 合计的既有不变式对豆包成立；gaps 原样渲染；其他 9 个 Agent 视图零回归。
- 产出：commit + 平滑替换 daemon。

### P4 · 加固与终验

- 边界测试：文件轮换、compaction 追平、多 Profile、损坏块容错、配置热切换。
- 24h soak：内存 / 句柄 / 日志零异常 / tick 耗时分布达标。
- 文档：README.agent.md（目录树 / 注册表 / 路由表 / Cookbook 增补豆包条目与"采集型适配器"新范式说明）、README.md 用户侧开关说明。
- 版本号与发版按 `docs/发版指引.md` 另行决策（本计划不含发版）。
- 产出：commit + 最终平滑替换 + 验收报告（§6 表格逐项实测回填）。

## 8. 明确不做的事

- 不移植开源 841 行 IndexedDB 读取器（热路径用不上 V8 全量反序列化，冷路径只需 ~60 行 Snappy）。
- 不改 Swift / 不重编译 Dock App / 不新增常驻进程或线程。
- 不 Hook 网页 API、不做浏览器自动化、不联网上报——纯本地只读豆包存储。
- 不虚构 output / cache / 模型名；不追求"补齐"数据源固有缺口。
